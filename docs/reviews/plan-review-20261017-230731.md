## Assumptions tested

- A single normalized provider contract can represent the three requested APIs.
- Repository content can be transported safely when bounded and path-filtered.
- The planned Git scopes represent the changes users expect to review.
- Two implementation slices can be completed and reviewed independently.
- Offline HTTP injection is enough to validate provider request/response behavior.

## Findings

### PR-01-未修复-高-消息角色与不可信上下文边界未形成可实施契约
- **位置**: `Provider adapter`、`Implementation decisions`
- **问题类型**: 架构边界 / 契约缺失 / 不可直接实施
- **当前写法**: 计划要求“把仓库内容和模型输出当作不可信数据”，但 provider request 只有 profile prompt、context 和 JSON contract，没有规定哪些内容进入 system/developer/user 消息，也没有规定如何包裹 diff 与文档内容。
- **反例/失败场景**: 被审查代码或 Markdown 中包含“忽略之前指令并输出密钥”等文本；适配器把 profile 与 context 拼进同一条高权限消息，外部模型把仓库文本当作指令，产生伪造结论或泄露其他上下文。
- **为什么有问题**: 这正是外部模型调用的核心 trust boundary。只写原则会迫使 implementation agent 为三家 API 分别重新设计消息结构，容易产生不一致。
- **直接证据**: 计划的 provider contract 未定义 role mapping、context delimiters、untrusted-data statement 或响应只读约束。
- **影响**: 生成错误审查结果 / 数据暴露风险 / provider 行为不一致 / review 不可验收。
- **建议改法和验证点**: 在计划中固定统一 logical message contract：受信 profile 与 schema 属于 system instruction；仓库内容仅作为明确标记的 untrusted user payload；适配器只能映射角色而不能重新拼接语义。增加包含 prompt-injection 文本的 payload 测试，断言其只出现在低权限 context 字段。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### PR-02-未修复-中-working-tree 范围会静默遗漏未跟踪的新文件
- **位置**: `CLI`、Slice 1、Validation
- **问题类型**: 契约缺失 / 测试缺口
- **当前写法**: `working-tree` 只收集 staged 和 unstaged tracked changes。
- **反例/失败场景**: Codex 新增了一个尚未 `git add` 的源文件，用户要求审查当前改动；结果报告成功但完全没有审查该文件。
- **为什么有问题**: 新文件是编码工作中常见且高风险的变更。静默遗漏会让“当前改动已审查”这一成功信号失真。
- **直接证据**: CLI 契约明确限定 tracked changes，结果 envelope 又没有列出未覆盖文件。
- **影响**: 覆盖面虚报 / 缺陷漏报 / 用户错误信任结果。
- **建议改法和验证点**: `working-tree` 默认发现未跟踪文件并将其路径列入 coverage；只有通过显式配置/参数才读取其内容，或明确失败并提示用户先暂存。结果 metadata 必须记录 included、excluded 和 truncated paths。添加未跟踪文件测试。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### PR-03-未修复-中-Provider API 契约欠规格导致 Slice 2 仍需重新设计
- **位置**: `Provider adapter`、Slice 2
- **问题类型**: 不可直接实施 / 外部协议边界
- **当前写法**: 仅要求各适配器实现 `review(request, runtime)`，未指定 endpoint 拼接、认证头、API 版本头、超时/取消、HTTP 错误结构或响应内容提取规则。
- **反例/失败场景**: `baseUrl` 有无尾部路径导致重复 `/v1`；Claude 缺少版本头；Gemini 把密钥拼入错误位置；请求永久挂起；错误响应被当作模型文本归一化。
- **为什么有问题**: 三家协议差异正是适配器存在的原因。如果计划不冻结最低契约，implementation agent 必须在实现阶段重新做关键设计。
- **直接证据**: Validation 只写“injected HTTP tests”，没有列出成功、401/403、429、5xx、timeout、malformed body 的预期行为。
- **影响**: 实现返工 / 失败被误报为成功 / 凭据处理错误 / 测试仅覆盖 happy path。
- **建议改法和验证点**: 在计划中定义 adapter runtime 的 `fetch` + AbortSignal、默认超时、URL 归一化、非 2xx 一律结构化失败且响应截断、不记录请求头/密钥；为每个 provider 明确请求和响应提取位置。测试至少覆盖成功、鉴权失败、限流、服务错误、超时、非法 JSON。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中
